# Monitoring the VM cluster

Self-contained on the kubeadm VM cluster rather than federated into the kind
cluster's Grafana, so the VM cluster stands alone as a complete environment.

| Component | Namespace | Address |
|---|---|---|
| metrics-server | `kube-system` | - |
| kube-prometheus-stack (`kps`) | `monitoring` | - |
| Grafana | `monitoring` | http://192.168.0.241 (MetalLB) |
| Longhorn UI | `longhorn-system` | http://192.168.0.240 (MetalLB) |

Values: [`k8s/vm-cluster/kps-values.yaml`](../k8s/vm-cluster/kps-values.yaml)

## metrics-server is not Prometheus

|  | metrics-server | Prometheus |
|---|---|---|
| Serves | `metrics.k8s.io` - what `kubectl top` and the HPA call | its own API, queried with PromQL |
| Retains | last ~15 seconds, in memory | weeks, on disk |
| Scope | node and pod CPU/memory only | anything exposing `/metrics` |

They are not alternatives. A cluster with Prometheus and no metrics-server has
working dashboards, a broken `kubectl top` and a broken HPA.

## metrics-server on kubeadm: the x509 failure

Symptom: pod `0/1 Running` with **no restarts**, and
`kubectl top nodes` returns `error: Metrics API not available`.

`0/1 Running` with no restarts means the container started cleanly and is
failing its readiness probe - it is failing at its job, not crashing. Read the
logs, not `--previous`.

    Failed to scrape node err="Get \"https://192.168.0.203:10250/metrics/resource\":
    tls: failed to verify certificate: x509: cannot validate certificate for
    192.168.0.203 because it doesn't contain any IP SANs"

Port 10250 is the kubelet. kubeadm issues CA-signed certificates for the API
server, etcd and the front proxy - but not for the kubelet's serving endpoint.
Each kubelet self-signs its own, with no IP SANs. metrics-server is the first
component that verifies it, and correctly refuses.

Lab fix applied:

```
kubectl -n kube-system patch deployment metrics-server --type=json \
  -p='[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'
```

Cost: metrics-server now accepts any certificate on 10250.

Production fix, still outstanding: set `serverTLSBootstrap: true` in the kubelet
config, restart the kubelets, approve the resulting CSRs with
`kubectl get csr` / `kubectl certificate approve`.

## `up == 0`

`up` is generated by Prometheus itself - one series per target, `1` if the last
scrape succeeded. `up == 0` lists everything it cannot reach, and is the first
query to run on an unfamiliar cluster.

A missing target is **silent**: the dashboard panel is simply empty, with no
error anywhere.

Six targets were down on first install:

| Job | Instance | Port |
|---|---|---|
| kube-controller-manager | .201 | 10257 |
| kube-scheduler | .201 | 10259 |
| kube-etcd | .201 | 2381 |
| kube-proxy (x3) | .201 .202 .203 | 10249 |

One root cause: kubeadm binds all of these to `127.0.0.1`, while the chart's
ServiceMonitors target the node's real IP. Deliberate kubeadm hardening - the
chart assumes someone has already opened it.

Fixed for the controller-manager and scheduler:

```
sudo sed -i 's/--bind-address=127.0.0.1/--bind-address=0.0.0.0/' \
  /etc/kubernetes/manifests/kube-controller-manager.yaml \
  /etc/kubernetes/manifests/kube-scheduler.yaml
```

No restart is issued. These are static pods; the kubelet watches
`/etc/kubernetes/manifests` and reconciles on file change. That is the whole
difference from a Deployment, and why you cannot `kubectl delete` your way out
of a broken control plane.

That directory is mode 0700 root: write access to it is root on the cluster,
since anything placed there runs as a control-plane pod. Put `sudo` on the
`grep` as well as the `sed`.

Security cost: those metrics ports now answer on the LAN. They still require a
valid ServiceAccount token, but on a real cluster you would restrict them with a
NetworkPolicy or host firewall rather than binding to every interface.

Still outstanding:

- etcd - add `--listen-metrics-urls=http://0.0.0.0:2381` to `/etc/kubernetes/manifests/etcd.yaml`
- kube-proxy - set `metricsBindAddress: 0.0.0.0:10249` in the `kube-proxy` ConfigMap, then `kubectl -n kube-system rollout restart ds/kube-proxy`

## Sizing

`longhorn-2` keeps two replicas, so **every PVC consumes twice its size** from
the 78Gi pool. 10 + 5 + 2Gi of claims uses 34Gi. This doubling is the thing
most often forgotten when sizing replicated storage.

`kubectl top` reports the current **working set** as a percentage of
**allocatable** - unrelated to the `requests` the scheduler uses. A node can
read 20% here and still refuse to schedule a pod.
